# NetDesign AI — Project Memory (CLAUDE.md)

You are the primary implementation engine for NetDesign AI, a SaaS that converts
natural-language network requirements into: (1) a validated network design,
(2) an interactive topology diagram, (3) a metadata-rich .vsdx export,
(4) vendor-specific BASE configurations, and (5) an HLD/LLD specification document.

The founder works ~20 hrs/week in 2–3 hour sessions. Optimize every answer for
session-resumability: leave the repo green, update TODO.md before ending, and
prefer plans the founder can review in 5 minutes.

## Architecture (modular monolith — NOT microservices)

- `apps/web` — Next.js 14+ (App Router, TypeScript), Tailwind, React Flow for diagrams
- `apps/web/api` — Next.js API routes: auth, projects, generation orchestration, billing
- `services/vsdx` — small Python FastAPI service; ONLY place Python is used
  (vsdx library for .vsdx generation). Deployed separately (Railway/Fly.io).
- `packages/design-engine` — TypeScript. Deterministic rules: IP allocation,
  VLAN assignment, redundancy patterns, validation. THE MOAT LIVES HERE.
- `packages/config-gen` — Jinja2-style templates (nunjucks in TS) per vendor,
  rendering design JSON → base configs. LLM NEVER writes config lines directly.
- `packages/schema` — the design JSON schema (design-schema.json) + zod validators.
  This schema is the contract between ALL modules. Change it only deliberately,
  with a version bump.
- Database/auth/storage: Supabase (Postgres). Billing: Stripe. Analytics: PostHog.
- LLM: Claude API. Role: extract intent from user prose → design-parameters JSON.
  It proposes; the design engine disposes.

## The pipeline (memorize this)

user prose → [LLM: intent extraction] → design-params JSON
→ [design-engine: rules + validation] → design JSON (schema-valid)
→ [React Flow renderer] interactive diagram
→ [services/vsdx] .vsdx export
→ [config-gen] per-vendor base configs
→ [doc-gen] HLD/LLD markdown → docx

## Hard rules

1. Every generated design MUST validate against design-schema.json before
   rendering or export. Fail loudly with a human-readable reason.
2. IP addressing is computed deterministically by the engine (no LLM math).
   No overlapping subnets, ever. Loopbacks, P2P links, and mgmt nets follow
   the allocation rules in packages/design-engine/README.
3. Config templates are deterministic. LLM may draft a NEW template for human
   review, but runtime config generation is template-render only.
4. Every config output begins with the banner comment:
   "! Base configuration generated by NetDesign AI — validate in a lab before production."
5. .vsdx output must pass the structural validator AND stay green in the
   golden-file tests (tests/golden/*.vsdx compare on shape count, connects,
   embedded shape-data fields).
6. Never touch Stripe/billing code without flagging it for founder review.
7. Secrets only via environment variables; never commit them.

## Golden test scenarios (all must pass before ending a session)

- G1 branch-office: 2 routers (HSRP), 2 access switches, 1 firewall, 3 VLANs, /24s
- G2 campus: collapsed core, 6 access switches, wireless controller, voice VLAN
- G3 dc-leaf-spine: 2 spines, 4 leaves, VXLAN/EVPN intent, /31 fabric links
- G4 smb-simple: 1 router, 1 switch, 1 firewall, guest + corp VLANs
- G5 dmz: edge firewall pair, DMZ segment, reverse proxy, inside/outside zones
- G6 hybrid-cloud (phase 4): site-to-site VPN to AWS VPC, on-prem G4 topology

Run: `pnpm test:golden`. A session may not end red.

## Conventions

- TypeScript strict; zod at every boundary; no `any`.
- Conventional commits. Small PR-sized changes even without PRs.
- Session ritual: (a) read TODO.md, (b) propose a plan, wait for approval on
  multi-file changes, (c) implement, (d) run tests + lint, (e) update TODO.md
  with state + next step, (f) one-paragraph summary of what changed.
- When uncertain about a NETWORKING decision (design rule, config syntax),
  ASK the founder — they are the domain expert. When uncertain about a
  CODE decision, pick the boring option and note it.

## What NOT to build yet (scope guard)

No SSO, no teams/RBAC beyond owner, no mobile, no config *deployment*,
no marketplace, no i18n, no microservices split. Say no on the founder's behalf.
